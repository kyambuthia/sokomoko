Feature guide

Asiliano demo

Sokomoko is a multi-vendor marketplace with a customer storefront, partner workspace, operations console, and JSON API. This guide describes the codebase and the demo currently running at asiliano.online.

For riders & couriers

Courier sign in

Operations staff assign shipped orders to a courier. Each courier account sees its own assigned jobs and the information needed to deliver them.

Dispatch

Admins and staff assign or reassign an order before pickup. Failed attempts return to dispatch for review and reassignment.

Rider workflow

Couriers mark an order picked up, out for delivery, delivered, or unsuccessful. A fixed reason is required for a failed attempt; dispatch can then reassign it.

Private job data

Riders see only their own assigned customer name, delivery address, and item quantities. Completed job history hides the delivery address. Payment details and item prices are not shown.

Account access

An admin creates each courier login without email. Couriers can change their password after signing in.

Dispatch is manual. Couriers can message the buyer of an assigned delivery. The codebase does not include GPS tracking or route optimization.

This demo publishes no courier login. The live courier workspace is available for deployments that provision courier accounts; no real deliveries are accepted here.

Local services

Directory

The codebase supports seller offerings alongside products, with the same storefront design and partner workspace.

Find a local offering

Browse services by title, business, category, neighbourhood and where the service happens. Open any service to browse other published offerings from the same business. Listings show duration, currency, fixed or starting price, or quote-only pricing, and whether the offering is at a business, mobile or remote.

Seller controls

Create a private draft, preview the saved listing, publish it in the directory or archive it. Shop ownership is enforced on the server, and stale edits cannot overwrite a newer version. Buyers can open encrypted enquiries from a published service.

Demo services are sample content. No appointments, sales or payments are accepted. Maps, distance search, practitioner calendars, and professional verification remain future work. Do not submit health information.

Handles & messages

Buyer · shop · courier

Each username is also an @handle. Open Messages to find an exact buyer or seller handle, or contact someone from a product, service, order, or assigned delivery.

Message requests

Send one introduction by handle. The recipient accepts before the conversation continues. Product, service and order conversations open with their marketplace context.

Shop inbox

Approved devices of authorized shop members receive future sessions after recipient review. New devices do not inherit earlier history. Each seller has a separate conversation when an order includes multiple shops.

Delivery conversations

Buyers and their assigned courier can chat. Reassignment opens a new conversation and removes the former courier's access. Completed delivery conversations become read-only.

Block & report

Block a contact across conversations or explicitly disclose selected received text for moderator review. Admins review the reported message without opening the rest of the chat.

New messages are encrypted on approved browser devices using MLS. Review device fingerprints before trusting a contact. Older server-readable history remains separately labeled. Password reset cannot recover lost messaging keys. Shared demo accounts are for sample information only.

Messaging remains a demo implementation without an independent cryptographic audit. The Rust dependency audit has unresolved advisories; algorithm restrictions reduce exposure but do not resolve them. Developers should review the dependency security findings before considering a production release.

For developers

Source code

Application

Go 1.26.10, standard net/http, and html/template. Server-rendered pages use CSS and ES modules without a frontend bundler.

JSON API

Versioned /api/v1 endpoints cover the catalog, account, cart, checkout, orders, messaging, admin operations, partner tools, and courier deliveries.

Data

PostgreSQL 17 via database/sql and pgx. SQL migrations, templates, and static assets are embedded in the binary.

Local development

Use docker compose up --build, or make run with PostgreSQL. The repository docs/ folder covers configuration, architecture, development, and deployment.

API conventions

JSON responses use a data/error envelope, paginated lists, session authentication, and CSRF tokens for state-changing requests. Public catalog reads use short cache windows.

Security & payments

Code capabilities
  • Password hashes use bcrypt; sessions use random tokens stored as hashes.
  • Role checks and partner data scoping protect workspace actions.
  • Courier queries are scoped to assignments owned by the signed-in courier; delivery transitions are validated and recorded in an append-only event history.
  • CSRF protection applies to state-changing forms and API calls.
  • Request limits and login abuse backoff are included.
  • Production responses set security headers; Caddy terminates HTTPS.
  • Configured payment provider credentials are encrypted at rest.

Payment adapters

Cash on delivery · M-Pesa Daraja · Paystack

The code includes provider callbacks, payment confirmation, reconciliation, and refund workflows. Payment routes are disabled in this demo.
